# بررسی و بهینه‌سازی بخش هایلایت

این بررسی روی موتور هایلایت، یادداشت‌ها، بازیابی متن، مدیریت ذخیره‌ها و نمایش فهرست در popup انجام شده است. هدف، کاهش توقف صفحه هنگام بازیابی تعداد زیاد هایلایت و حفظ اطلاعات در برابر تغییر محتوای سایت است. وابستگی تازه‌ای اضافه نشده؛ آزمایش‌ها از Playwright موجود در پروژه استفاده می‌کنند.

## یافته‌های نسخه قبلی

| یافته | اثر عملی | تغییر انجام‌شده |
| --- | --- | --- |
| ساخت index متن و بازیابی به‌صورت همگام انجام می‌شد. | در صفحه بزرگ، thread اصلی تا پایان بازیابی فرصت اجرای frame و تعامل را از دست می‌داد. | index و بازیابی به قطعه‌های کوتاه با واگذاری کنترل به event loop تقسیم شدند. |
| مسیرهای مبتنی بر ID با XPath سراسری، حتی برای ID حذف‌شده، بررسی می‌شدند. | بررسی مسیر شروع، پایان و fallback می‌توانست بارها کل درخت صفحه را جست‌وجو کند. | ID مستقیم با `getElementById` و ادامه مسیر با XPath نسبی حل می‌شود؛ XPath عمومی برای مسیرهای دیگر باقی است. |

| جست‌وجو و فیلتر popup خواندن و پردازش تکراری اطلاعات را ایجاد می‌کرد. | تایپ جست‌وجو با تعداد زیاد ذخیره‌ها پرهزینه می‌شد. | snapshot فهرست cache می‌شود، تغییرات storage آن را به‌روز می‌کنند و جست‌وجو debounce دارد. |
| بستن popup هنگام فعال‌شدن tab دیگر می‌توانست ادامه عملیات «نمایش» را قطع کند. | صفحه باز می‌شد ولی پرش به هایلایت تا پایان بازیابی قابل اتکا نبود. | تحویل درخواست به worker و ذخیره موقت آن تا تأیید یافتن و پیمایش Range انجام می‌شود. |

موتور CSS native در نسخه قبلی نیز وجود داشت. بهبود اصلی این تغییر، زمان‌بندی بازیابی، مسیر سریع ID، تغییر تدریجی registry و کنترل چرخه عمر است؛ صرف وجود CSS Highlights نتیجه تازه این کار نیست.

## معماری نسخه بهینه

### نمایش و تغییرات کوچک

مسیر اصلی از `Range` و `CSS.highlights` استفاده می‌کند. طبق [MDN](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Custom_Highlight_API)، این روش بدون تغییر ساختار DOM صفحه متن را رنگ می‌کند و چند Range می‌توانند در یک مجموعه قرار بگیرند. قابلیت در مرورگرهای جدید از ژوئن ۲۰۲۵ Baseline است؛ پشتیبانی نسخه‌های قدیمی با feature detection بررسی می‌شود.

مجموعه هر رنگ فقط هنگام نیاز تغییر می‌کند؛ برای اضافه یا حذف یک هایلایت، مجموعه‌های دیگر بازسازی نمی‌شوند. پاک‌سازی فقط کلیدهای متعلق به افزونه را حذف می‌کند و هایلایت‌های خود سایت باقی می‌مانند. حالت hover و انتخاب فعال نیز به‌صورت موقت روی Range اجرا می‌شود. برای hit testing، API جدید `highlightsFromPoint` در صورت وجود استفاده می‌شود و مسیر مبتنی بر caret و index متن برای مرورگرهای فاقد آن باقی است. این API جدیدتر هنوز پشتیبانی یکسان با موتور نمایش ندارد. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HighlightRegistry/highlightsFromPoint)، [مستند انتشار Edge 140](https://blogs.windows.com/msedgedev/2025/09/25/unlock-text-editing-use-cases-with-highlightsfrompoint/)

### بازیابی قابل کنترل

ابتدا مسیر DOM و offset بررسی و متن واقعی آن با متن ذخیره‌شده تطبیق داده می‌شود. اگر مسیر قابل اعتماد نبود، quote و متن قبل/بعد در ریشه مناسب جست‌وجو می‌شوند. context و موقعیت برای تشخیص متن‌های تکراری استفاده می‌شوند و اتصال سراسری مبهم پذیرفته نمی‌شود. استاندارد [W3C TextQuoteSelector](https://www.w3.org/TR/annotation-model/#text-quote-selector) نیز exact، prefix و suffix را برای تمایز متن تکراری تعریف می‌کند. [مقاله رسمی Hypothesis](https://web.hypothes.is/blog/fuzzy-anchoring/) نمونه‌ای از ترکیب چند selector را شرح می‌دهد؛ مقاله مربوط به ۲۰۱۳ است و اثبات همه جزئیات پیاده‌سازی فعلی آن محصول نیست.

index هر ریشه در همان کار بازیابی به اشتراک گذاشته می‌شود. نگاشت موقعیت متن نرمال‌شده به offset خام DOM حفظ می‌شود؛ انتخاب میان چند نود، فاصله‌ها و ارقام فارسی/عربی نباید به offset اشتباه تبدیل شود. نودهای بسیار بلند نیز در قطعه‌ها پردازش می‌شوند تا ساخت یک آرایه بسیار بزرگ در یک مرحله انجام نشود. ریشه‌های پنهان یا نامناسب و UI افزونه از جست‌وجوی متن کنار گذاشته می‌شوند.

بودجه هدف هر قطعه کار حدود **۶ میلی‌ثانیه** است؛ پس از مصرف بودجه، کار با timer کوتاه کنترل را به مرورگر پس می‌دهد. این عدد، سقف تضمین‌شده تمام کارهای مرورگر، paint، layout، XPath عمومی یا garbage collection نیست. نسخه حاضر از scheduler کوچک داخل پروژه استفاده می‌کند و به `requestIdleCallback` وابسته نیست. این API طبق [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback) برای کار کم‌اولویت مناسب است اما هنوز در همه مرورگرهای رایج پشتیبانی یکسان ندارد.

### تغییرات صفحه و چرخه عمر

MutationObserver موجود صفحه دوباره استفاده می‌شود؛ observer اضافه برای اسکن دائمی کل صفحه ساخته نمی‌شود. mutation متن و حذف نود به indexهای نود/اجداد مرتبط وصل می‌شود تا هایلایت‌های تحت تأثیر dirty شوند. تغییرات UI افزونه فیلتر می‌شوند. اگر ریشه‌ای که در حال index شدن است تغییر کند، کار جاری لغو و بازیابی بعدی با تأخیر افزایشی محدود زمان‌بندی می‌شود. تغییر نامرتبط بیرون ریشه نباید کار سالم را دائماً از ابتدا شروع کند. [گزینه‌های رسمی MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver/observe)

هر کار به epoch، pageKey و وضعیت فعال‌بودن قابلیت وابسته است. خاموش‌کردن یا جابه‌جایی route، timerهای کار و Rangeهای افزونه را پاک می‌کند؛ ادامه یک promise قدیمی اجازه بازگرداندن UI یا هایلایت مسیر قبلی را ندارد. indexهای موقت پایان کار آزاد می‌شوند. mutationهای ناشی از fallback خود افزونه نیز با observer هماهنگ می‌شوند تا حلقه بازسازی ایجاد نکنند.

### مدیریت ذخیره‌ها و مسیر نمایش

رکورد خراب مانع رکورد معتبر بعدی نمی‌شود و به‌صورت خودکار پاک یا بازنویسی نمی‌شود. اگر متن در صفحه حذف یا جابه‌جا شده باشد و اتصال قابل اعتماد پیدا نشود، متن و یادداشت ذخیره‌شده در بورد باقی می‌ماند. حذف، تغییر رنگ و یادداشت روی ID مستقل عمل می‌کنند؛ overlap دو هایلایت، حذف یکی را به حذف دیگری تبدیل نمی‌کند. فیلتر صفحه/سایت/یادداشت، خروجی JSON و بازگرداندن حذف از بورد در دسترس‌اند.

در popup، جست‌وجو از snapshot حافظه استفاده می‌کند و تغییر واقعی storage آن را اصلاح می‌کند. migration رکوردهای قدیمی همچنان ID پایدار تولید می‌کند. عملیات بازکردن هایلایت ذخیره‌شده به service worker سپرده می‌شود؛ درخواست برای tab هدف در `chrome.storage.session` می‌ماند، پس بسته‌شدن popup یا تعلیق worker آن را زود از بین نمی‌برد. درخواست فقط بعد از تأیید پیدا شدن Range و پیمایش آن، مصرف می‌شود و tab بسته‌شده نیز پاک‌سازی دارد.

## اندازه‌گیری عملکرد

مقایسه با commit پایه `86c0621ef0063a2e4a08fa4c5bcc5ca02d4dd71e` در Chromium `149.0.7827.55` روی Windows انجام شد. داده خام در `logs/highlight-benchmark.json` است؛ این مسیر طبق `.gitignore` وارد مخزن نمی‌شود. فایل گزارش hash منبع‌های واقعی و رکوردهای fixture را نگه می‌دارد.

شرایط یکسان دو نسخه: **۱۸٬۰۰۰ نود متن در body و ۳۰۰ هایلایت یکتا با XPath منقضی‌شده**، سه اجرای جدا برای هر نسخه، ترتیب متناوب، صفحه headless تازه، CSS native فعال و فقط `highlight-manager.js` با storage/runtime شبیه‌سازی‌شده. زمان از نخستین بررسی مسیر ذخیره‌شده بعد از دریافت storage تا پایان ثبت Rangeها و finalization اندازه‌گیری شد. ساخت fixture، layout اولیه، تزریق فایل و تأخیر storage وارد زمان نشدند؛ سایر ماژول‌های افزونه نیز اجرا نشدند.

| معیار؛ میانه سه اجرا | نسخه پایه | نسخه بهینه |
| --- | ---: | ---: |
| زمان کل بازیابی | ۸٬۵۳۹٫۱ ms | ۸۹۰٫۳ ms |
| callbackهای RAF هنگام خود بازیابی | ۰ | ۱۰۱ |
| بیشترین فاصله RAF در بازه بازیابی | ۸٬۵۳۹٫۱ ms | ۱۴٫۲ ms |
| تعداد Long Task با مدت حداقل ۵۰ ms | ۱ | ۰ |
| بیشترین مدت Long Task | ۸٬۵۴۱ ms | ۰؛ موردی ثبت نشد |
| هایلایت دقیق بازیابی‌شده در هر اجرا | ۳۰۰ از ۳۰۰ | ۳۰۰ از ۳۰۰ |

در همین fixture، زمان میانه حدود **۹٫۶ برابر** کمتر شد. هر دو نسخه همه متن‌ها را دقیق و با رنگ native بازیابی کردند؛ mark جدیدی ایجاد نشد و همه ۱۸٬۰۰۰ نود متن اصلی متصل باقی ماندند. تفاوت مهم دیگر، فرصت اجرای frame در حین کار بود: نسخه پایه تا پایان کار هیچ RAF اجرا نکرد و نسخه بهینه در میانه کار به مرورگر فرصت داد.

این نتایج به همین سناریوی ساختگی، سخت‌افزار، نسخه مرورگر و snapshot ثبت‌شده وابسته‌اند و تضمین سرعت همه سایت‌ها یا رتبه‌بندی رقبا نیستند. اندازه‌گیری RAF، اندازه‌گیری input latency نیست. فاصله اولیه/نهایی در مرز بازه نیز محاسبه می‌شود؛ در نسخه همگام بدون RAF، این فاصله همان مدت مسدودبودن است. API Long Tasks کارهای کمتر از ۵۰ ms را ثبت نمی‌کند. پس از تغییر منبع، benchmark باید دوباره اجرا شود؛ hash گزارش اجازه تشخیص snapshot اندازه‌گیری‌شده را می‌دهد.

## اعتبارسنجی و اجرای دوباره

**۱۴ تست متمرکز هایلایت و ۲ تست navigation به‌صورت مجموعه‌ای پاس شدند.** در بازاجرای نهایی نیز **۱۶ تست منتخب پس‌رفت** و آزمون مستقل لغو/تلاش دوباره ترجمه پاس شدند. مجموعهٔ گسترده‌تر RTL و remaster هم بررسی شد: ۷۵ تست در اجرای گستردهٔ اولیه پاس شدند و موارد باقی‌مانده پس از اصلاح تشخیص کلیک و به‌روزرسانی ابزارسنجی مسیر ID، با اجرای متمرکز دوباره بررسی و پاس شدند. آزمون زمان‌بندی لغو ترجمه که در اجرای موازی شکست خورده بود، در اجرای مستقل دوباره پاس شد. این اعداد تعداد اجرای تست‌اند و با هم جمع نمی‌شوند؛ برخی سناریوها مشترک‌اند.

پوشش شامل انتخاب چندنودی و حفظ هویت گره‌های متن، reload، حذف و بازگشت متن، ورودی‌ها و انتخاب کیبورد، overlap، حفظ هایلایت خود سایت، fallback بدون بازسازی بی‌پایان، تغییر route یا disable هنگام بازیابی بزرگ، رکورد خراب، متن بلند در مرز قطعهٔ ۲۰۴۸ نویسه‌ای و نرمال‌سازی فارسی است. API تشخیص موقعیت که در محیط isolated نتیجهٔ خالی می‌دهد نیز با کلیک واقعی و حذف آزموده شد. بسته‌شدن popup، تأخیر ظهور متن، ack قدیمی، استفاده دوباره از tab و پاکسازی tab بسته‌شده آزمون مستقل دارند.

در تست یکپارچهٔ افزونه، ۳۰۰ هایلایت روی ۱۸٬۰۰۰ گرهٔ filler در اجرای نهایی حدود ۸۷۱ ms بازیابی شدند و ۶۸ frame در حین بازیابی پیش رفتند؛ این سناریو سایر ماژول‌های افزونه را نیز دارد و با جدول مستقل بالا یکسان نیست.

بررسی syntax تمام فایل‌های تغییرکرده و `git diff --check` موفق بود. `npm run build` و lint استاندارد پروژه نیز موفق شدند؛ lint هشدارهایی دربارهٔ الگوهای قدیمی و متغیرهای استفاده‌نشده دارد، اما خطای lint ثبت نشد. بررسی جداگانهٔ هفت فایل تغییرکرده هم بدون خطا پایان یافت.

```powershell
npx playwright test tests/highlight.spec.js tests/highlight-navigation.spec.js --workers=1 --reporter=line

# تست‌های remaster
npx playwright test tests/remaster.spec.js --workers=1 --reporter=line

# زیرمجموعه هشت‌تایی قبلی مرتبط با هایلایت و ذخیره
npx playwright test tests/rtl.spec.js --grep "Highlight|Popup persists|31\.|43\.|44\." --workers=1 --reporter=line

# مقایسه مستقل پایه Git و فایل جاری
node tools/highlight-benchmark.js --runs=3 --nodes=18000 --highlights=300 --baseline-ref=86c0621ef0063a2e4a08fa4c5bcc5ca02d4dd71e

npm run build
```

## محدودیت‌های مشخص

- در مرورگر فاقد CSS Highlights یا برخی ریشه‌های Shadow DOM، fallback مبتنی بر `mark` به‌کار می‌رود و ساختار DOM را تغییر می‌دهد. صحت متن و پاک‌سازی این مسیر تست شده، اما هزینه و سازگاری آن دقیقاً مشابه مسیر native نیست.
- استخراج/بازیابی سراسری داخل همه Shadow DOMها، iframeها، PDF viewer داخلی مرورگر و صفحه‌های محافظت‌شده مانند `chrome://` تضمین نمی‌شود. وجود قابلیت PDF در محصولات مقایسه‌شده به معنی پیاده‌سازی آن در این پروژه نیست.
- `pageKey` فعلی برای سازگاری با ذخیره‌های قبلی از host بدون `www`، path، query و hash route ساخته می‌شود؛ protocol و port را تفکیک نمی‌کند. جداسازی کامل این حالت‌ها به migration داده نیاز دارد و در این تغییر انجام نشده است.
- quote، context و مسیر، بازیابی را مقاوم‌تر می‌کنند اما متن حذف‌شده یا چند نسخه غیرقابل تشخیص یک جمله را نمی‌توان با قطعیت بازسازی کرد. داده ذخیره‌شده حفظ می‌شود؛ قرارگرفتن رنگ روی متن نامربوط راه‌حل محسوب نمی‌شود.
- `::highlight()` فقط مجموعه محدودی از خصوصیات متن و رنگ را می‌پذیرد؛ border، radius یا blur عمومیِ یک span مستقیماً قابل انتقال نیست. همچنین معنای ساختاری و دسترس‌پذیری خودکار ایجاد نمی‌کند؛ فهرست و کنترل‌های قابل استفاده با کیبورد همچنان لازم‌اند.
